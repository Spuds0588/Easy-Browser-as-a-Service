YES YOU CAN — embed the app that refuses to be embedded.

One Web Component. One stateless container. A real remote Chromium streams into your page over WebSocket — its cookies and localStorage stay isolated from yours, its network calls never touch your origin, and the session survives a reload of your page.

You have already tried the iframe.

The app you need lives behind a vendor that will not open up: no API, no CORS header, and a frame policy that blocks you outright. That is the whole reason this exists.

Blocker 1

It refuses to be framed

X-Frame-Options: DENY or a frame-ancestors CSP stops an iframe dead. Here the page is rendered by a browser you control, so there is no frame policy to satisfy — it is a canvas, not an iframe.

Blocker 2

Its cookies collide with yours

Two apps on one origin fight over localStorage, session cookies and third-party cookie rules. Each remote session gets its own incognito browser context, so its storage never mixes with your app's.

Blocker 3

Its APIs ignore your origin

No CORS headers means no direct calls. The remote browser does the talking from inside your infrastructure, so your page never needs to reach the vendor's API at all.

This is a remote browser, not a magic header. The vendor's terms, licence and acceptable use still apply, and the browser runs on your network — see SECURITY.md before you point it at anything sensitive.

Three steps to embed

The SDK is a plain Custom Element that behaves like an iframe. No framework, no bundler, no npm install required in your app.

1

Run the service

git clone https://github.com/Spuds0588/Easy-Browser-as-a-Service.git
cd Easy-Browser-as-a-Service
./install.sh

Docker is used when its daemon is reachable, otherwise Node runs it on the machine. It prints Up: http://localhost:8080/demo.html when the health check passes, along with the access-control signing key it generated and a ready-to-paste embed snippet that already has a token in it.

2

Mint a token, then load the SDK

# trade your signing key for a short-lived token
curl -sX POST -H "Authorization: Bearer $RBAS_KEY" \
  "http://localhost:8080/api/token?ttl=15m"
# {"token":"v1.eyJ…"}   (or: node server/token.js --ttl 15m)
<!-- in your page: tokens expire, so mint one per load -->
<script>
  const SERVICE = 'http://localhost:8080';
  fetch('/rbas-token').then(r => r.json()).then(({ token }) => {
    const s = document.createElement('script');
    s.src = `${SERVICE}/sdk.js?token=${encodeURIComponent(token)}`;
    document.head.append(s);
  });
</script>

One file, served by the container itself. The service opens no browser without a valid token, and the token is short-lived — so mint it in your backend (with RBAS_KEY, or your own HMAC-SHA256) and inject the tag at runtime rather than pasting it into the HTML. The bundled demo page at /demo.html already gets one injected for you.

No backend at all? A static page or a packaged app has nothing to mint with. Allow-list its origin and its network instead, drop the token from the script URL, and the element asks the service for one itself: 

# the service itself: allow-list who may ask
RBAS_TRUSTED_ORIGINS=https://app.example.com
RBAS_TRUSTED_NETWORKS=10.0.0.0/8

<!-- no ?token= : the element mints its own -->
<script src="https://browser.your-company.com/sdk.js"></script>

Both halves matter. RBAS_TRUSTED_ORIGINS stops other websites — a browser sets Origin and page JavaScript cannot forge it. RBAS_TRUSTED_NETWORKS stops everyone else: Origin is not a secret, so a non-browser client that can reach the port could set it to anything. Tokens minted this way are capped at 15 minutes.

3

Drop in the element

<remote-browser
  src="https://legacy-crm.internal"
  style="display:block; width:100%; height:640px"
></remote-browser>

Give it a height: the element's measured size becomes the remote viewport. Optional attributes: server when the SDK is hosted on another origin, and storage-key to keep session state under a different name.

Talking to the element

const rb = document.querySelector('remote-browser');

rb.addEventListener('ready', (e) => console.log('session', e.detail.sessionId, e.detail.resumed));
rb.addEventListener('download', (e) => console.log('user downloaded', e.detail.filename));

rb.navigate('https://legacy-crm.internal/accounts/42');
rb.reload();                   // back to src
console.log(rb.status);        // { ready, sessionId, url }

// end it now instead of waiting for a timeout
rb.endSession();               // fires 'ended', no reconnect

Events: ready, navigate, clipboard, download, expired and ended. Mouse, wheel, keyboard, text clipboard and file pickers are wired up for you. endSession() closes the remote browser immediately — no reconnect grace, no idle timer to wait out.

What is actually inside

Everything here is implemented over the Chrome DevTools Protocol on one master Chromium — no WebRTC, no STUN/TURN, no per-user browser process.

Access control, built in

Every session needs a short-lived HMAC-signed token minted from your server's RBAS_KEY, so an anonymous visitor cannot open a browser. Tokens gate /ws, uploads and downloads directly — no reverse proxy required.

Screencast, not video

JPEG frames from CDP Page.startScreencast stream over a WebSocket and are drawn to a canvas. Quality and frame size are tunable; each frame is acknowledged.

Real input passthrough

Clicks, movement, drag and wheel scrolling, plus keyboard events, mapped onto Input.dispatchMouseEvent and Input.dispatchKeyEvent with coordinates scaled to the remote viewport.

Text clipboard both ways

Copy in the remote page to get a clipboard event on the host, and paste on the host straight into the focused remote field. Text only, by design.

Uploads and downloads

A remote file picker is intercepted and turns into a real picker on your page; remote downloads are captured in the container and handed back as a short-lived link.

Sessions survive reloads

Reload your page and the same remote session is re-attached (60 s reconnect grace by default). Cookies and localStorage are replayed from the host, so the user stays logged in.

Stateless, and reclaimed

The container holds nothing durable: no database, no volume. Idle, hidden and disconnected sessions are reaped, and bridged files expire after five minutes.

Isolated by construction

One browser process for the whole box, one incognito context per connection. Isolation is per session; memory grows with sessions, not with browser processes.

Drop-in, dependency-free SDK

A single vanilla JavaScript file registering <remote-browser> with Shadow DOM. No React, no Vue, no bundler, no build step anywhere in the product.

Deploy it like any container

One image, one port, nothing to persist. The interesting constraints are shared memory and WebSocket support. 

# one command, then http://localhost:8080/demo.html
./install.sh

# or straight compose, on another host port
PORT=9000 docker compose up -d --build

# or plain docker
docker run -d --name rbas -p 8080:8080 \
  --shm-size=1gb easy-browser-as-a-service

Ships with Dockerfile, docker-compose.yml, fly.toml and install.sh. Full deployment guide →

  • Port 8080 by default, overridable with PORT.
  • WebSocket /ws must pass through your proxy with upgrades intact.
  • Shared memory --shm-size=1gb (512 MB minimum) or Chromium renderers crash.
  • Writable /tmp the upload/download bridge lives there and cleans up after itself.
  • Healthcheck GET /healthz; the image declares it already.
  • Access tokens sessions need a short-lived token signed with RBAS_KEY; unset, the service generates and logs one at boot.
  • Memory budget roughly 1 GB per concurrent session; MAX_SESSIONS defaults to 8.
  • TLS terminate at your proxy — the SDK upgrades to wss:// from the origin you give it.
  • Scaling scale to zero freely; multiple replicas need sticky routing on /ws to keep resume working.

What it deliberately does not do

Worth knowing before you wire it into something important.

Secure, but not a sandbox

A token authenticates a caller, not a person, and it is checked when a session starts rather than continuously. The browser also runs on your network, so keep token lifetimes short, mint them per user, and restrict what the container can reach.

No audio, images or WebRTC

Video frames carry no sound, clipboard sync is text-only, and streaming is deliberately WebSocket-based because WebRTC needs STUN/TURN infrastructure to deploy.

No persistence to rely on

Session state lives in the host page's localStorage, and restarting the container drops live sessions. There is no database to back up — or to lose.

Questions people ask before the first embed

Short answers to the things that decide whether this is the right tool. The FAQPage structured data in this page's head is generated from exactly this text.

Can it embed a site that blocks iframes with X-Frame-Options or CSP?

Yes, because nothing is ever framed. The container's Chromium opens the site as a top-level page in its own incognito browser context, renders it to JPEG frames, and streams those to a canvas on your page. X-Frame-Options, CSP frame-ancestors and CORS never come into it.

Does this get around CORS?

It removes the need for CORS rather than bypassing it. Your page never calls the target's API: the container's browser talks to the target directly, and your page only talks to this service over a WebSocket. All of the service's HTTP responses send Access-Control-Allow-Origin: *, so the SDK works from any embedding origin.

What happens when the user reloads the page?

The session resumes. The SDK stores {sessionId, url, localStorage, cookies} in the host page's localStorage and replays it on connect, and the server keeps the dropped session's browser context alive for RECONNECT_GRACE_MS (60 seconds by default). Reconnecting with the same session id re-attaches that context, so the user stays logged in instead of starting over.

Is anything about the session stored on the server?

No. The server is stateless: no database and no volume. Session state lives in the host page's localStorage, bridged upload and download files live in the container's tmp directory and are deleted after five minutes, and restarting the container drops the live sessions rather than losing anything durable.

How many sessions can run at once?

MAX_SESSIONS controls it and defaults to 8. Each session is one incognito browser context inside a single master Chromium process, so memory grows with sessions rather than with browser processes — budget roughly 1 GB of memory per concurrent session. A session beyond the limit is refused with Could not start session: capacity reached (N/N) — try again shortly. To run more than one session on the same host page, give each <remote-browser> its own storage-key attribute.

Is it safe to expose the service to the internet?

Safer than it is often assumed to be, but still not a public sandbox. Every session needs a short-lived signed token minted from your server's RBAS_KEY, so an anonymous visitor cannot open a browser. But a token authorizes a caller, not a person, and the browser still runs on your network and can reach whatever it can reach. Keep token lifetimes short, mint tokens per user in your backend, and restrict the egress of the container.
